## 一、架构设计

### 整体架构

```
                           ┌─────────────────┐
                           │    各端（微信/    │
                           │  桌面/元宝/其他） │
                           └───────┬─────────┘
                                   │ 简芯请求()
                                   ▼
                    ┌────────────────────────────┐
                    │   并联负载均衡层（客户端）   │
                    │   随机选端口 → 超时重试     │
                    └────────────┬───────────────┘
                                 │
             ┌───────────────────┼───────────────────┐
             ▼                   ▼   
     ┌──────────────┐   ┌──────────────┐   
     │ HTTP 节点 1   │   │ HTTP 节点 2   │   未来可扩展 8502+
     │ 端口 8500    │   │ 端口 8501    │   
     ├──────────────┤   ├──────────────┤   
     │ 简芯HTTP守护  │   │ 简芯HTTP守护  │   
     └──────┬───────┘   └──────┬───────┘   
            │                  │
            └──────┬───────────┘
                   │ 读同一份文件（当前阶段）
                   ▼
         ┌─────────────────────┐
         │   中枢数据/ 目录     │
         │ (6维索引 + 权重)    │
         │ (消息/群聊目录)      │
         └─────────────────────┘
```

### 当前阶段：并联双通道 + 单数据源

两台服务器指向 **同一份本地文件**（`中枢数据/`）。这是过渡状态。

原因：先突击实现服务器层的并联，数据层还没时间做。

### 关键设计点
1. **同一份文件** — 双服务读取同一磁盘目录，不存在 A 新版 B 旧版的问题
2. **零同步成本** — 不需要镜像/复制，自然地一致性
3. **互不抢占** — 每个服务独立端口，独立进程，各自读写
4. **故障透明** — 客户端随机选端口，超时/失败自动重试另一个

## 二、选型决策：并联（双通道同时工作）

> 选型人：系统设计者（叶子）

| 方案 | 描述 | 为什么没过 |
|:----|:------|:----------|
| 主备自动切 | 8500 干活，8501 待命，主崩自动切换 | 备用闲着浪费，需要心跳检测，复杂 |
| 双接口公布 | 给各端两个地址，自己选 | 负载不均 |
| **并联双通道 ✅** | **两个服务同时接待请求，随机路由，超时重试** | **选中** |

**为什么选并联：**
1. 两个服务都已经跑着了，放着浪费不如一起用
2. 并联天然抗崩——崩一个剩下一个继续干，比主备切换更快（不需要心跳检测）
3. 吞吐翻倍——多端查询时不挤一条通道
4. 实现零成本——客户端加几行随机路由+失败重试就行，不需要负载均衡器

### 客户端调用逻辑

```
简芯请求('/status') → 随机重排 [8500, 8501]
                    → 试第一个端口
                      → 成功？返回结果
                      → 失败？试下一个端口
                        → 成功？返回结果
                        → 全部失败？返回 None
```

所有端（微信端、桌面端、元宝端、其他）统一使用 `简芯客户端.py` 封装。

## 三、冷启动时序

```
Python 启动 → zst_import 激活 → 加载简芯模块 → 
神经网络初始化 → 扫描记忆文件（10-15秒）→ 
HTTPServer 绑定端口 → 响应请求
```

**冷启动后秒回。** 初始化慢是因为 TF-IDF + 线性模型训练需要扫描所有已记忆内容。

## 四、维护指南

### 启动/重启
```bash
# 一键启动双服务（杀旧+启动+验证）
python 简芯HTTP守护_双服务.py

# 或手动分别启动
python 简芯HTTP守护.py --port 8500
python 简芯HTTP守护.py --port 8501
```

### 投喂新数据
```bash
curl -X POST http://localhost:8500/feed \
  -H "Content-Type: application/json" \
  -d '{"text":"新的记忆内容","source":"用户"}'
```

### 检查状态
```bash
curl http://localhost:8500/status
curl http://localhost:8501/status
```

### 搜索测试
```bash
curl "http://localhost:8500/search?q=关键词"
```

### Python 客户端用法
```python
from 简芯客户端 import 简芯请求

# GET 请求
状态 = 简芯请求('/status')
结果 = 简芯请求('/search', params={'q': '记忆'})

# POST 请求
结果 = 简芯请求('/feed', method='POST', 
               data={'text': '新内容', 'source': '测试'})
```

## 五、故障排查清单

**当 HTTP 服务器不可用时，按顺序排查：**

| 步骤 | 检查项 | 命令/方法 | 常见原因 |
|:---:|:------|:---------|:--------|
| 1 | 进程是否存活 | `tasklist \| findstr python` | 进程崩溃，重启即可 |
| 2 | 端口是否监听 | `netstat -ano \| findstr :8500` | 端口被占 / TIME_WAIT |
| 3 | 另一个是否正常 | `curl localhost:8501/status` | 并联设计，一个挂了用另一个 |
| 4 | 都不正常 | 手动 `python 简芯HTTP守护.py` 看报错 | zst_import 没装上？模块缺失？ |
| 5 | Python 版本/依赖 | `python -c "import zstandard"` | pip 安装 zstandard |
| 6 | 防火墙 | `telnet localhost 8500` | 检查防火墙规则 |

### 常见故障处理

#### 端口占用 / TIME_WAIT
```
场景：Kill 旧进程后立即启动新服务 → 端口被占
原因：Windows TIME_WAIT 约 2-4 分钟
解决：等待或使用不同端口（如 8502）
预防：双服务启动脚本已处理（杀旧 → 等 3 秒 → 启动）
```

#### 一个服务挂了
```
并联架构天然容错：客户端自动重试另一个端口
修复：重新启动挂了的那台即可，不影响其他端使用
```

#### 神经网络初始化慢
```
场景：冷启动 10-15 秒无响应
原因：TF-IDF + 线性模型训练
解决：等待初始化完成
预防：无，神经网络初始化必须完成才能绑定端口
```

## 六、未来规划：数据层多源

### 为什么当前是单数据源

现在两台服务器指向同一份本地文件。这是**突击阶段**的过渡设计——先让功能跑起来，数据层的优化放在后面。

### 愿景架构

```
                    ┌───────────────┐
                    │  并联负载均衡  │
                    │  (随机路由)    │
                    └───────┬───────┘
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │ HTTP节点1 │      │ HTTP节点2 │      │ HTTP节点N │
   │ 端口8500  │      │ 端口8501  │      │ 端口8502+ │
   └─────┬────┘      └─────┬────┘      └─────┬────┘
          │                 │                 │
          │  (未来：各节点   │                 │
          │  可指向不同      │                 │
          │  数据源)         │                 │
          ▼                 ▼                 ▼
   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │ 主存储    │      │ 副本/缓存 │      │ 本地备份  │
   │ (COS云端) │      │ (云盘)    │      │ (本机)    │
   └──────────┘      └──────────┘      └──────────┘
```

### 为什么要数据也多源

1. **云端最安全** — COS 对象存储 + 云盘，数据不丢
2. **本地当备份** — 网络断了本地还能干活
3. **多节点读不同源** — 不同服务器读不同数据源，天然冗余
4. **弹性扩展** — 需要更多容量就加节点、加存储源

### 现在不做

这是未来规划，不是当前任务。目前数据量还没到需要折腾 NAS 和 COS 的程度。等需要时再接入。

### 关键决策记录

| 决策 | 选项 | 选择理由 |
|:----|:----|:---------|
| 服务器模式 | 主备 vs 并联 | **并联**。双通道同时工作，抗崩不浪费 |

| 客户端封装 | 随机路由+重试 vs 负载均衡器 | **随机路由+重试**。零外部依赖，几行代码搞定 |
